1. 3-Tier Enterprise Web Architecture

The Velora AI Smart Hotel Management Platform is architected following the classic enterprise-grade 3-Tier Model-View-Controller (MVC) paradigm. The system guarantees high cohesion and loose coupling by isolating presentation rendering, business heuristics, and persistent data access into discrete boundaries without relying on bloated full-stack frameworks.

Architectural Layer Responsibilities

  • Presentation Layer: Dynamic JavaServer Pages (JSP) using JSTL tags and Expression Language (EL). Encapsulates modern responsive CSS with Vercel-inspired monochromatic tokens, Geist typography, and zero external frontend dependencies.
  • Controller Layer: Lightweight HttpServlet controllers handling incoming HTTP requests, session lifecycle management, request validation, and view forwarding. Protected by an intercepting AuthenticationFilter enforcing strict Role-Based Access Control (RBAC).
  • Business & AI Logic Layer: Standalone domain services executing business operations (dynamic revenue management, staff workload balancing, entity extraction, aspect sentiment tracking) and orchestrating Google Gemini API prompts.
  • Persistence Layer: Data Access Object (DAO) pattern isolating SQL operations behind parameterized JDBC PreparedStatement objects, preventing SQL Injection vulnerabilities.

4.2 3-Tier Multi-Model Failover Cascade

To guarantee enterprise uptime and prevent system crashes during API rate limits or outages, GeminiService.java implements an automatic 3-tier cascade paired with deterministic heuristic fallbacks:

1. Primary Request: gemini-3.5-flash-lite (Sub-second inference, low token cost) | +--> (If HTTP 429 Rate Limit / Timeout) v 2. Secondary Failover: gemini-2.5-flash (Ultra-reliable Long-Term Stable model) | +--> (If Model Unavailable) v 3. Tertiary Failover: gemini-3.5-flash (Full-scale thinking model) | +--> (If Cloud Network Completely Unreachable) v 4. Local Fallback: Deterministic Rule-Based Heuristic Engine - Keyword & Regex Departmental Mapping - Statistical Occupancy Multipliers for Pricing - Template-Based Professional Reassurance Copy * The platform NEVER crashes; guest stay workflows continue 100%!

4.3 Prompt Engineering & Output Optimization Parameters

  • Low Temperature (0.2): Applied across all analytical JSON endpoints (Complaint Classification, Service Extraction, Review Sentiment, Dynamic Pricing) to eliminate stochastic hallucinations and enforce factual classification.
  • Token Budgeting (1024 Tokens): Calibrated to permit complete multi-line JSON structures (with room category rationales and aspect decompositions) without risking token cutoff.
  • Resilient Substring JSON Parsing: Extracts text bounded strictly between the first { and last } index, safeguarding the Gson parser against markdown code fence contamination (e.g. ```json ... ```).

5. Technical Architecture Viva Defense Guide

Comprehensive architectural Q&A covering Artificial Intelligence, Software Engineering, Database Systems, and Enterprise Security:

Category A: Artificial Intelligence & LLM Integration

Q1: Where exactly is Artificial Intelligence implemented in your project?
AI is integrated across six operational subsystems: 1. Stage 14: Complaint Classification & Severity Triage.
2. Stage 15: Service Request Entity Extraction (quantities, items, preparation ETA).
3. Stage 16: Velora AI Virtual Concierge (multi-turn guest chat with stay context).
4. Stage 17: Operations Analytics & Executive Briefing Generation.
5. Stage 18: Aspect-Based Review Sentiment Analysis across 5 hotel dimensions.
6. Stage 19: Dynamic Pricing & Revenue Optimization Engine (RMS).
Q2: How do you prevent LLM Hallucinations in the hotel system?
We employ three guardrails: 1. Strict Domain System Prompts: Directs the model strictly to hotel operational facts and enforces raw JSON output.
2. Low Temperature (0.2): Minimizes entropy to ensure deterministic, reproducible outputs.
3. Heuristic Validation: Extracted fields (categories, priorities, pricing deltas) are validated against Java Enums and database constraints before application.
Q3: What happens if the Gemini API goes down or the hotel loses internet?
The platform executes a Deterministic Algorithmic Fallback Engine. Every AI service catches IOExceptions and timeouts, instantly switching to localized rule-based logic (regex departmental mapping, occupancy demand multipliers, and template replies). The application never crashes and guest transactions proceed uninterrupted.
Q4: How does Aspect-Based Sentiment Analysis differ from traditional sentiment analysis?
Traditional sentiment returns a flat label (Positive/Negative). A review stating "The steak was amazing, but check-in was delayed and the room AC was noisy" is often flattened into Neutral. Aspect-Based Sentiment decomposes the review into discrete operational vectors: Cleanliness, Staff Hospitality, Room Quality, Food & Beverage, and Value for Money, identifying exact departmental deficiencies.
Q5: How does the AI Dynamic Pricing formula calculate optimal tariffs?
The engine evaluates: 1. Current Occupancy Velocity (>70% triggers Surge Capture; <40% triggers Demand Stimulation). 2. Day-of-Week Multipliers (incorporates weekend leisure premiums). 3. Gemini Strategic Analysis: Suggests bounded percentage deltas while respecting price ceiling and floor parameters.

Category B: Software Engineering & Design Patterns

Q6: What architectural pattern does this application implement?
The system implements the enterprise Model-View-Controller (MVC) pattern: Model: POJO domain entities (Room, Booking, Task, Review) and DAO persistence classes.
View: Clean JSP pages rendering HTML5, modern CSS, and dynamic JSTL data.
Controller: Java Servlets (HttpServlet) handling HTTP requests, session security, and service orchestration.
Q7: What design patterns are used throughout the codebase?
1. Data Access Object (DAO): Isolates SQL operations behind clean interfaces (RoomDAO, BookingDAO).
2. Intercepting Filter: AuthenticationFilter guards all endpoints to enforce Role-Based Access Control.
3. Singleton / Shared Resource: DBConnection and SHARED_HTTP_CLIENT reuse pooled connections.
4. State Machine: Controls room lifecycles (Available → Reserved → Occupied → Cleaning → Available).
Q8: Why did you use pure Java Servlets & JSP instead of Spring Boot?
Using native Java EE Servlets and JSP provides low-level mastery over request-response lifecycles, HTTP sessions, connection pooling, and multi-threaded servlet execution without the heavy abstraction layers, high memory footprint, or auto-configuration overhead of Spring Boot.
Q9: How does the Automated Task Assignment Engine distribute workload?
In TaskAssignmentService.java, when a guest submits a service request or complaint, the system identifies the target department (e.g. Housekeeping), queries available staff in that department, selects the employee with the lowest active workload, assigns the task, marks the employee as BUSY, and dispatches a notification.

Category C: Database Systems, Transactions & Security

Q10: How do you prevent double-booking of rooms during concurrent reservations?
Room availability is queried using strict date-range overlap SQL: NOT (check_out_date <= ? OR check_in_date >= ?) for active bookings. The reservation insert and room state updates are executed inside an atomic transaction with conn.setAutoCommit(false). If a conflict occurs, the transaction rolls back cleanly.
Q11: How do you prevent SQL Injection attacks?
All database queries across every DAO class strictly use PreparedStatement with parameterized inputs (? placeholders). Raw user input is never concatenated into SQL strings, ensuring the MySQL query planner treats parameters exclusively as literal values.
Q12: How are user passwords and database credentials secured for production?
User passwords are encrypted using 12-round BCrypt salt hashing (PasswordUtil.java). Passwords are never stored in plaintext. Database and API credentials are resolved dynamically via System.getenv() and uncommitted .env files, ensuring zero credentials exist in the Git repository.
